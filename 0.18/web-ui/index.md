# Web UI and sign-in

Purgatorium has a small web UI (`http://p9m.<HOST_DOMAIN>`, or `UI_HOST`) for creating and managing sandboxes without the API directly, alongside the REST API.

Only the admin

Users have no web UI: they get and use their sandboxes from Claude Code ([`/p9m:init`](https://csakaszamok.github.io/p9m/0.18/claude-plugin/index.md)). A user who signs in sees only how to install the plugin; the sign-in is for approving `/p9m:init` (and for apps open only to signed-in people, see [App access](https://csakaszamok.github.io/p9m/0.18/app-access/index.md)). A user's sign-in reaches no API either: users work with tokens. What follows is the admin's UI.

The users have an address of their own, `sbx.<HOST_DOMAIN>` by default (`USER_HOST`, see [Configuration](https://csakaszamok.github.io/p9m/0.18/configuration/index.md)): they sign in and approve `/p9m:init` there, and `UI_HOST` is the admin's only.

Two ways to sign in:

- **Admin**: a local account, set via `ADMIN_USER` / `ADMIN_PASSWORD`. Signs in with the "Administrator sign-in" form, which is there only with `ADMIN_LOGIN=on` (off by default: for emergencies), and sees every sandbox (My area + All sandboxes). Everyday, the admin signs in with OIDC, from an address in `OIDC_ADMIN_EMAILS`.
- **Signed out for doing nothing**: after 30 minutes without a click, a key or a scroll (`SESSION_IDLE_TIMEOUT`), with a warning two minutes before; the header shows the time left next to the user's name; the automatic refreshes of the list do not count, so a tab left open does not stay signed in.
- **Against guessing**: an address with 5 failed admin password sign-ins within 15 minutes has to wait 1 minute, then 2, 4… up to an hour after each further failure; after 30 failed admin passwords in an hour from all addresses together, the admin password is refused for everyone until the hour is over (OIDC still works). Failed OIDC sign-ins are only logged, never counted: a callback cannot be guessed, and a room behind one address (a workshop, an office) would lock itself out with a few wrong accounts. Every refusal is logged as `[login] <address>: …`, e.g. for fail2ban. The address is the one Traefik saw; the counts are kept in memory (a restart forgets them).
- **Everyone else**: OIDC (Google or any OpenID Connect provider). Configure `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET` and register the redirect URI `$PUBLIC_URL/auth/callback` (and the users' address's, `https://<USER_HOST>/auth/callback`, by default `https://sbx.<HOST_DOMAIN>/auth/callback`, too) with the provider — character for character (scheme, no trailing slash), under Google's *Authorized redirect URIs*, otherwise sign-in fails with `redirect_uri_mismatch`. Google accepts `http://` redirect URIs only for `localhost`, so with Google use an `https://` `PUBLIC_URL` (locally: a self-signed `*.lvh.me` certificate in `certs/` and `PUBLIC_URL=https://p9m.lvh.me`, see [HTTPS](https://csakaszamok.github.io/p9m/0.18/https/index.md)). `OIDC_PROVIDER_NAME` labels the sign-in button (default `Google`). Signed-in users only see their own sandboxes.

`SESSION_SECRET` signs the session cookie — set it to a long random string; sessions issued under an old value stop working if it changes.

`OIDC_ALLOWED_DOMAINS` or `OIDC_ALLOWED_EMAILS` says who may sign in and create sandboxes (e.g. `example.com`): with OIDC on, Purgatorium refuses to start without one of them, since with Google any Google account would get in. `OIDC_ALLOW_ANYONE=true` lets anyone with an account at the provider in, if that is what you want. An account not on the list is told so on the sign-in page; one taken off the list is signed out, and its tokens stop working, once Purgatorium restarts with the new list. Each user may have `SANDBOX_QUOTA` sandboxes running at once (default 3, `0` = unlimited), guaranteed, and with `SANDBOX_QUOTA_MAX` more while the server has room to spare for the others' guarantees (*Running 4 / 3 · up to 10* beside **New sandbox**); asleep, deep-sleeping and archived ones are not counted, so letting a sandbox sleep frees its place, and the admin is not limited. At the limit a user can neither create a sandbox nor wake one, from sleep or deep sleep: its address shows *Running limit reached*, its address shows *Running limit reached* with the running sandboxes, and **Wake** in the panel lets the owner put one to sleep instead (`POST /sandboxes/:name/start` with `{"sleep": "<name>"}`). Purgatorium never puts a sandbox to sleep on its own. Running sandboxes' web addresses do not go through Purgatorium: they keep working while it is down; waking needs it, and so do the TLS TCP addresses and Docker access (they go through Purgatorium's TCP gateway). `SANDBOX_MAX_TOTAL` (default 200) caps the running sandboxes on the whole server, the admin's included (asleep ones take no place): when it is reached nobody but the admin can create one or wake one (*The server is full*). The sign-in page shows the sandbox places above the sign-in buttons (taken and free; `LOGIN_CAPACITY=off` hides them), and once signed in the top bar does, on every page (e.g. *142 / 200 places*, the free ones on hover; orange from 90%, red when full). The **Overview** page shows the counts as cards: running of how many allowed, asleep, deep sleep and archived; for the admin the sandbox places used against the server limit (the admin's own sandboxes take places too), the host's CPU and memory (used now and reserved by running sandboxes), the disk use, a table per owner and a **Users** table. Users lists every account that has signed in (by e-mail; `admin` for the local admin): when it was last seen (a page load, at most every 10 minutes), its last sign-in and how many, its sandboxes now and created, and its last API use (its tokens); *no sandbox yet* marks someone who signed in but never created one. The rows are kept in `data/user-stats.json` until the admin deletes one (**Delete**: only the row; the account and its sandboxes stay). Only the admin sees them (`GET /users`, `DELETE /users/:account`).

Users get their tokens from Claude Code: each `/p9m:init` approval makes one for that sandbox only, valid 90 days, in the project's `.p9m` folder. From **My area → Access tokens** (`/settings/tokens`), the admin can mint a personal access token (`p9m_…`) for agents to use as `Authorization: Bearer p9m_…`; the token acts as the admin for the API. The full token is shown once, at creation. Tokens can be set to expire in 30 days, 90 days, or never. The page lists every account's tokens, and the admin can revoke any of them, e.g. one a user lost: users cannot.

A token can also be limited to one sandbox (**Access** in the dialog, or **Token for this sandbox…** on a sandbox panel's **Access** tab). Such a token lists and opens only that sandbox, and can start, stop and restart it and change its sleep times; it cannot create or delete sandboxes or manage tokens (403), and any other sandbox answers 404. Deleting the sandbox leaves the token in place: if you restore the sandbox, it works again.

With such a token an agent can deploy and update apps in the user's sandbox: the Purgatorium API gives it the sandbox's Docker client certificates, and the `docker` command line reaches the sandbox's own Docker daemon (or, in a sandbox from the `portainer` template, the Portainer API). Step by step: [agent guide](https://csakaszamok.github.io/p9m/0.18/agent-guide/index.md).

## Simple and Advanced

The top bar has a **Simple | Advanced** switch, remembered for the admin (starting in Advanced). Simple is for when you only want apps online: the menu shows *My area* only (your sandboxes, without its tabs); the list shows the name, status, *Sleeps in* and age; a new sandbox asks for a name and a template; a sandbox panel has **Wake** or **Sleep**, an **App ports** tab (the web address of each app and **Let your agent deploy…**: the Claude Code plugin or a zip for other agents, the same window as in Advanced, which adds its **Options**) and a **Details** tab (when it last ran, the sleep times, warnings, archiving). Advanced shows everything: Overview, tokens, SSH keys, the Terminal and Logs, and the Containers, Access, Files, Resources and Registry tabs. Simple only hides: what an account may do is the same in both, and the API and MCP do not change. `PUT /me/view` with `{"view": "simple"}` or `{"view": "advanced"}` sets it; `GET /me` returns it as `view`, and whether the account may switch as `view_switch`.

## Light and dark

The pages follow the device's light or dark setting until the account chooses one with the sun / moon button in the top bar; the choice is remembered for the account, so it holds on any computer. The sign-in page, before anyone is signed in, always follows the device. The page shown while a sandbox wakes up, the error pages, the terminal and the log view stay dark. `PUT /me/theme` with `{"theme": "light"}`, `"dark"` or `"system"` sets it; `GET /me` returns it as `theme` (`null`: the device decides).

## Host folders

The admin can mount folders of the host into a sandbox, e.g. a shared data folder, when `HOST_MOUNT_ROOTS` lists where they may come from (e.g. `HOST_MOUNT_ROOTS=/srv/shared`; see [Configuration](https://csakaszamok.github.io/p9m/0.18/configuration/index.md)). On a sandbox panel's **Resources** tab, **Host folders** lists them, with **Remove** for each, and a form to add one: the host folder (at or under one of the roots), where it appears in the sandbox (empty: `/mnt/<last part of the host path>`) and **read-only**. The folder is bind-mounted into the sandbox container, so the apps in the sandbox's own Docker can bind it from there too (e.g. `/mnt/shared:/data`).

Adding or removing one recreates the sandbox container, after a confirmation: a running sandbox restarts (its apps are unreachable for a few seconds), an asleep one stays asleep, one in deep sleep gets the change when it wakes. A host folder that does not exist is not created: Docker refuses it, the panel shows Docker's message and nothing changes. The target cannot be `/`, a system directory (`/etc`, `/usr`, `/proc`, `/dev`, `/run`…) or on, above or under one of the sandbox's own mounts (`/var/lib/docker`, `/opt`, `/root`, `/home`, `/srv`, …). The mounts are kept in the sandbox's compose file (and its `p9m.mounts` label), so they survive sleep, deep sleep and upgrades.

**A mount gives whoever owns the sandbox that host folder**, as root, and every app and agent in it: mount read-only what they need not change, and only what they may see. The owner can list them through the API (`GET /sandboxes/:name/mounts`); only the admin adds or removes them, on the **Resources** tab (in Simple, **Details** lists them). With `HOST_MOUNT_ROOTS` unset no mount can be added; ones already there stay until the admin removes them. API: `GET`, `POST` and `DELETE /sandboxes/:name/mounts` (see [API](https://csakaszamok.github.io/p9m/0.18/api/index.md)), over MCP `list_sandbox_mounts`, `add_sandbox_mount` and `remove_sandbox_mount`.
