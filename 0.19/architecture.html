Purgatorium architecture

Traefik v3.6 routes requests; Sablier measures idle time and puts a sandbox to sleep. Purgatorium creates sandboxes, wakes every sleeping one (within the owner's limits), takes long-asleep ones into deep sleep, and archives them on an explicit delete. A running sandbox's web traffic does not go through Purgatorium. Nothing is ever deleted automatically.

Known weak spots

  • Waking needs Purgatorium: while Purgatorium is down, running sandboxes keep serving web traffic, but no sandbox can be woken, and TLS TCP addresses and Docker access (through its TCP gateway) do not work.
  • Restart policy: after a wake, only inner containers with restart: unless-stopped or always start again (an accepted, documented trade-off).
  • Activity: web requests and open Docker connections keep a sandbox awake; a TLS TCP connection alone (e.g. a database client) does not, and drops when the sandbox sleeps.
  • Isolation: the default dind runtime is privileged; root inside a sandbox can reach the host. sysbox runs without it and is used in production; both share the host's kernel, and a Kata runtime (a VM per sandbox) is on the roadmap.
  • Archive size: the archive of a fresh sandbox is about 200 MB, and archives are never pruned automatically. DELETE is synchronous and can take minutes with a large volume.
  • Network limit: every running or asleep sandbox holds a Docker network; SANDBOX_MAX_TOTAL (default 200) keeps users within the daemon's address pools. Widen default-address-pools for more.
