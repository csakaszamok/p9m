    Purgatorium roadmap¶

    Open, not yet scheduled¶

    • A Kata Containers runtime, for untrusted code. Each sandbox in its own lightweight VM with its own kernel, so root inside a sandbox no longer means root on the host (today's dind runtime is privileged). Docker supports Kata through its containerd shim ("runtimes": {"kata": {"runtimeType": "io.containerd.kata.v2"}} in the host's daemon.json, then runtime: kata in the sandbox's compose service), so it fits next to dind and sysbox as a third runtime with the same wiring (FRP tunnel, Traefik route, Sablier, docker_data volume, archive). To work out:
    • the host needs hardware virtualization (KVM): bare metal, or a cloud VM with nested virtualization;
    • dockerd inside the Kata VM: privileged there applies to the VM only, not the host, but must not pass the host's devices through;
    • the docker_data volume and its performance (virtio-fs), and how the CPU and memory limits map to the VM's size;
    • a foxglove image for it, and the same integration tests as for the other runtimes;
    • still a sandbox (same API, lifecycle, quota and UI), with its isolation shown as a badge next to its name and chosen at create time ("Isolation: Container / MicroVM"): dind 🟠 privileged, sysbox 🔵 container, kata 🟢 microVM. "MicroVM" is said only where it is true: dind and sysbox sandboxes share the host's kernel.
    • GPUs in sandboxes. Today no sandbox sees a GPU. A sandbox could ask for one at create time, like CPUs and memory, and the list, the panel and the API would show which have one (a GPU column with the model, e.g. RTX 4090). It suits the sleep model: a sleeping sandbox could give its GPU back, and the next one to wake take it. To work out:
    • per runtime: dind needs the NVIDIA driver and nvidia-container-toolkit on the host, the device passed to the sandbox container and the toolkit in the foxglove image, so the inner Docker hands it on to the apps; whether and how sysbox (the production runtime) passes GPUs through, to check first; Kata only through VFIO, typically one GPU per VM;
    • detecting the host's GPUs at startup and in check-host.sh (nvidia-smi, Docker's runtimes);
    • limits and quota (SANDBOX_MAX_GPUS, the admin beyond), as for CPU and memory;
    • a whole GPU per sandbox, or shared (time-slicing, MIG);
    • what a waking sandbox does when every GPU is taken: wait, refuse, or start without one.
    • Every path into a sandbox through frp, next steps. Since 0.12.23 every path goes through the frp tunnel: web addresses (Traefik → <name>-socat:8080 → frps), and the TLS TCP addresses, Docker access and SSH (Traefik → Purgatorium's TCP gateway → the sandbox's frps on traefik-net, frpc's tcp proxies). frpc connects out of the sandbox, so the same wiring can carry sandboxes whose inside is not directly reachable: a microVM runtime (Kata, Firecracker), sandboxes on another machine or behind NAT, Kubernetes pods. Still open:
    • the TCP path still needs Purgatorium (its addresses do not answer while Purgatorium is down or upgrading, and open connections drop): whether Traefik could carry it with TCP routers to frps, which have no Sablier middleware;
    • one rule for staying awake on every path: traffic in the last minute, not an open connection (today: every web request; a -docker connection while bytes go through it, never waking a sleeping one, since Docker Desktop reconnects to every context at once; a -tcp connection not at all, though it wakes one);
    • sandboxes that are meant to talk to each other (one's app using another's database) do it through the TLS TCP addresses; an opt-in shared network is not there.
    • The Hub, next steps. The Hub lists the apps builders publish with a label. Still open: a webhook when an app is published (Slack, n8n, a Lemmy bot, without an RSS reader in between); a Hub per team, with Teams; a Hub open on the internal network without signing in, for small installs without single sign-on; p9m.publish.port to choose which of an app's ports it opens.
    • Deploy from git. Today a sandbox gets its apps through docker compose (the API, SSH, the Docker CLI or an agent). Next: connect a repository, and a push builds the image and deploys it into the sandbox, like a self-hosted Vercel; optionally a preview sandbox per branch or pull request, which sleeps like any other and is archived when the branch is merged. To work out:
    • where the build runs: in the sandbox's own Docker (its CPU and memory limits apply, and the image goes to the Purgatorium registry, which already scans pushes for secrets);
    • how Purgatorium reaches the repository and hears about pushes: a webhook from GitHub/GitLab/Gitea, or polling, and a deploy key per sandbox;
    • projects without a Dockerfile or a compose file: buildpacks (Nixpacks, Cloud Native Buildpacks), or refuse them with a clear message;
    • build logs in the panel and the API, and what a failed build does to the running version (it keeps running).
    • Coding agents inside a sandbox. Today the agent runs on the user's machine and drives a sandbox from outside (a token for that sandbox and its Docker keys in the project's .p9m folder). Next: the agent itself runs in a sandbox, like Docker Sandboxes (sbx) on a laptop, but on the team's server: it works next to its apps, and what it builds is at a URL for colleagues at once, which neither Coder (a workspace for writing code) nor an SDK sandbox gives. To work out:
    • an agent image: a foxglove variant with Claude Code, Node, uv and gh (not Docker's sandbox-templates image, which has no dockerd TLS listener, frpc or sshd), as a runtime next to sysbox; the user signs in over SSH at first;
    • sleep: a sandbox now sleeps after idle_timeout without web traffic, so a working agent would be stopped; an agent session must count as activity (a heartbeat, or a watch on its SSH / tmux session);
    • secrets outside the sandbox: an egress sidecar in the runtime's compose file, the sandbox's own network internal: true, and the model's key (ANTHROPIC_BASE_URL pointing at the sidecar) and a GitHub token (url.<sidecar>.insteadOf) added by the sidecar, so the agent never sees them; a per-user secret store in Purgatorium to fill them from; a domain allowlist for the rest of its traffic (the egress rules missing today);
    • starting and following a session from the UI: a web terminal, or Claude Code's remote control.
    • Teams: a sandbox owned by a group, so several people see and manage it, and other teams do not; optionally a quota per team.
    • A hard disk quota per sandbox. Today a sandbox above its disk limit is only flagged (see Disk). For a hard limit: its docker_data as a fixed-size ext4 image, loop-mounted through the local volume driver (type=ext4, o=loop); to work out: moving existing sandboxes' data, resizing (only while stopped), the archive, Docker Desktop. The Kata runtime gets this from its VM disk.
    • Kubernetes support: move the runtime layer behind the Docker-specific code; Sablier's Kubernetes provider helps here.
